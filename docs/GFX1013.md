# Experimental GFX1013 compute-queue profile

Release 0.13.1-2.2 keeps GFX1013 **opt-in, experimental and default-off**. It
retains the stock-first/Secure-Boot/rollback protections and incorporates the
exact-device 1.16 Fedora-kernel `%prep` dependency failure before any patched-boot
performance claim.

The package profile is `v0.2.5-alpha`, based on
`DryhoppedIPA/bc250-gfx1013-fix` `0.2.0-alpha` commit
`d3e6dc062c34d2523db0abe5741d1f5b0dea00d9`.

This package profile deliberately enables only:

- the three pinned V33 kernel compute-queue lifecycle patches; and
- private Mesa/RADV `0001-gfx1013-compute-queue-fix.patch` against exact Fedora 44
  `mesa-26.2.4-1.fc44` / Source0 `mesa-26.2.4.tar.xz`
  (`sha256:bce5f7fbebb934373b86c999a064d52fb5065878dc57f287f95346648ec832e9`).

Mesa 26.2.1 already upstreamed the GFX1013 GFX10.1 IP-version correction, so
profile v0.2.5-alpha no longer carries that stale hunk. The private patch now
contains only the still-required compute-queue exposure and async-compute
threadgroup workaround.

The optional upstream mesh/task patches, 40-CU changes, FSR changes, fan/power
policy and unrelated toolkit changes remain outside this profile. The existing
live CU manager remains a separate stock-AMDGPU feature.

The package carries `PATCH-SHA256SUMS` and `SOURCE-SHA256SUMS` under
`/usr/share/bc250-llm-server/gfx1013/upstream/`. `prepare` verifies both before
building. Exact Fedora kernel-source identity, exact `kernel-devel` ownership,
built-module SHA-256/vermagic/symbol-version evidence, stock module/initramfs
hashes, Mesa source identity and private RADV/ICD hashes are persisted in
root-owned lifecycle state. Module `srcversion`, when Fedora emits it, is retained
as supplemental evidence rather than treated as a universal module-load identity.

Three kernel identities are deliberately distinct. The patch/profile provenance
reference remains `7.2.9-200.fc44.x86_64`; the 0.13.1-2.2 package release-gate
qualification kernel is `7.2.10-200.fc44.x86_64`; and `prepare` always targets the
currently running exact kernel. A matching running/qualification kernel is reported
as `MATCH`, while the older patch reference is never described as the package
qualification kernel.

The Fedora release gate exercises the same kernel construction primitives used by
`prepare`: it selects the explicit release-contract qualification kernel-devel tree,
fetches the matching kernel SRPM, runs Fedora `%prep`, validates prepared-source
provenance, adapts only explicitly recognized relative AMD `TRACE_INCLUDE_PATH`
forms, applies the V33 patches with zero fuzz, builds/compresses `amdgpu`, and calls
the same module-identity validator as device `prepare`. Exact vermagic, module
SHA-256 and ABI evidence are mandatory at both boundaries; `srcversion` is recorded
when present but is supplemental. Mesa source preparation likewise prefers exact
`mesa.spec` and otherwise requires exactly one `mesa*.spec` candidate.

The RPM already requires `git-core` and `vulkan-tools`; GFX build preflight also
checks `git-core`, `redhat-rpm-config`, `kernel-srpm-macros` and the actual RPM
capability `rpm_macro(py3_shebang_fix)` explicitly. The capability is normally
provided by Fedora's `python3-rpm-macros`, but provider resolution is authoritative:
the preflight does not assume that one package name is the only valid provider.
Missing `%prep` macro capability blocks both `prepare --check` and normal `prepare`
before kernel/Mesa source acquisition or build work begins.

## Commands

Read-only state:

```bash
sudo bc250 gfx1013 status
sudo bc250 gfx1013 status --brief
sudo bc250 gfx1013 status --verbose
sudo bc250 gfx1013 status --json
```

Non-destructive prerequisites/rollback checks:

```bash
sudo bc250 gfx1013 prepare --check
sudo bc250 gfx1013 prepare --check --verbose
sudo bc250 gfx1013 prepare --download-only  # optional cache prefetch/resume
sudo bc250 gfx1013 disable --check
sudo bc250 gfx1013 reset --check
```

Lifecycle:

```bash
sudo bc250 gfx1013 prepare
sudo bc250 gfx1013 status
sudo bc250 gfx1013 stage-boot
# reboot once into the one-shot patched entry
sudo bc250 gfx1013 status
sudo bc250 gfx1013 enable
sudo bc250 gfx1013 disable
```

`prepare` is build-only: it does not write `/boot`, change GRUB selection or restart
services. `stage-boot` is the separate, explicit boot-activation transaction.

Recovery from orphaned/invalid package-owned GFX state:

```bash
sudo bc250 gfx1013 reset
```

`reset` is deliberately not a force-delete operation. It must first prove and
commit a safe stock saved/default **and next** boot path. If that authority
cannot be established, reset refuses destructive cleanup.

## Lifecycle states

Default `status` is operator-focused: lifecycle state, running kernel, prepared
kernel/profile, boot mode, private-RADV state, integrity summary, build-dependency
summary and next action. `status --brief` is the handover/harness form and omits
package/provenance internals. `status --verbose` retains the complete package,
upstream/Mesa, hashes, GRUB, provider and evidence detail. `status --json` remains
the machine-readable state contract.

All status modes expose the same top-level lifecycle state:

| State | Meaning |
|---|---|
| `DISABLED` | No package-owned prepared/active GFX1013 profile exists. |
| `PREPARED` | Exact-kernel artifacts are prepared; stock remains authoritative. |
| `PATCHED_BOOT_UNVERIFIED` | The marked one-shot patched boot is running, but `enable` has not committed it. |
| `ENABLED` | The verified patched boot is saved/default and Ollama private RADV is enabled. |
| `STOCK_REBOOT_REQUIRED` | A previous patched runtime is still loaded, but verified stock saved/default and next boot are already restored and the private runtime override is disabled; reboot completes the return to stock. |
| `ROLLBACK_REQUIRED` | State or boot authority is inconsistent and must be restored before promotion/reuse. |

Only `DISABLED` and `ENABLED` are stable qualification states. `PREPARED` and
`PATCHED_BOOT_UNVERIFIED` are intentionally transitional/incomplete.
`STOCK_REBOOT_REQUIRED` is a known safe rollback transition: stock boot authority is
already verified and only the currently loaded patched kernel remains until reboot.
`ROLLBACK_REQUIRED` remains the fail-closed recovery state for unknown authority
mismatches, interrupted transactions, invalid state or stale-kernel conflicts.

## Secure Boot policy

`prepare` determines Secure Boot state before any build/staging work. The
package-owned local `amdgpu` build is not automatically signed and the package
does not enroll a MOK key. Therefore:

- Secure Boot disabled: preparation may continue;
- non-EFI boot: preparation may continue;
- Secure Boot explicitly unsupported (`mokutil`: `This system doesn't support Secure Boot`): report `disabled-unsupported` and preparation may continue;
- Secure Boot enabled: preparation fails closed;
- Secure Boot state genuinely unknown on EFI: preparation fails closed.

An operator-managed signing/enrollment policy may be used outside this package,
but 0.13.1-2.2 deliberately does not automate trust enrollment or private-key
management.

## Exact-kernel preparation

`prepare --check` performs the non-destructive prerequisites check. Normal output
is intentionally exception-focused: it summarizes host/tooling and satisfied build
requirements, prints only missing dependency/capability blockers, keeps the two
integrity results, exact-kernel policy and source-cache readiness visible, then
ends with one result/fix/rerun section. Use `prepare --check --verbose` for the full
dependency/provider table and forensic prerequisite details.

Source-cache readiness includes cache hit/miss/partial state and approximate
download size when available. When either source is `MISS` or `PARTIAL`, the CLI
advertises `sudo bc250 gfx1013 prepare --download-only` as the optional resumable
prefetch step before the actual build. The prerequisite contract verifies, among
other things:

- Fedora/non-Atomic host policy;
- BC-250 PCI identity `1002:13fe`;
- package patch/full-source manifests;
- Secure Boot policy;
- required tools and build RPM/capability providers, including the Fedora Mesa Cargo toolchain (`cargo`, `rust`, `cargo-rpm-macros`) and `rpm_macro(py3_shebang_fix)`;
- exact `/lib/modules/$(uname -r)/build` ownership by
  `kernel-devel-$(uname -r)`;
- stock distro `amdgpu` module path;
- exactly one safe stock BLS entry for the running kernel;
- current saved/default boot is that stock entry;
- no conflicting upstream GFX1013 installation;
- no stale package patched-BLS/initramfs/private-RADV artifacts.

The mutating `prepare` builds **device-local artifacts** for the exact running
kernel; it does not regenerate or rewrite the GFX1013 patch set. It downloads/verifies
the exact Fedora kernel SRPM and runs that SRPM's own `%prep` in an isolated
rpmbuild tree. The package derives
every AMDGPU file touched by the V33 patch set, requires exactly one Fedora-prepared
source tree containing all of those targets, fingerprints those prepared files, and
uses that prepared tree itself as patch/build authority. It does not substitute
pristine Source0 or an SRPM-text heuristic for Fedora's downstream source
transformations. The package then adapts the AMD trace include paths deliberately
for an external-module build, applies the pinned V33 patches with zero fuzz and
builds `amdgpu`. Module compatibility verification
follows the exact kernel configuration: with `CONFIG_MODVERSIONS=y` it compares
required symbol CRCs; without modversions it requires exact vermagic plus all
strong imported symbols to resolve in the exact build tree's `Module.symvers`.
The latter is an exact-kernel symbol compatibility check, not a claim of complete
ABI equivalence. `.ko`, `.ko.xz`, `.ko.zst` and `.ko.gz` artifacts are supported.

Private RADV is built from exact Fedora `mesa-26.2.4-1.fc44`. The Fedora release
gate reconstructs the SRPM `%prep` tree and requires the carried Mesa patch to
dry-run/apply with zero fuzz. Runtime `prepare` repeats the exact SRPM/Source0
identity and patch checks before staging `/opt/bc250-gfx1013/...`.

The private Mesa build is intentionally **headless** for the Fedora LLM appliance.
It builds only the AMD Vulkan driver with an empty window-system platform list and
disables Gallium, X11/Wayland WSI, EGL, GBM, OpenGL, OpenGL ES, LLVM, video
codecs, Mesa Vulkan layers and Mesa tools. Meson fallback/subproject downloads are
disabled with `--wrap-mode=nodownload`. GUI-only development dependencies are not
part of the optional GFX build contract.

After Mesa installs into temporary staging, the package constructs a new minimal
private prefix containing only `lib64/libvulkan_radeon.so` and
`share/vulkan/icd.d/radeon_icd.x86_64.json`. `readelf` evidence is retained and
prepare fails before commit if RADV directly links X11/Wayland/related WSI client
libraries or carries RPATH/RUNPATH. The Fedora release gate also builds this exact
production headless path, so Meson-option/dependency drift is a release failure.

The private ICD is rewritten to reference the exact private
`libvulkan_radeon.so` path. It never relies on a system-wide Mesa replacement.

### Transaction boundary

Fedora kernel `%prep`, external module compilation, compatibility verification and
the Fedora-prepared Mesa build happen under a temporary root first. `prepare`
commits only the validated prepared module/evidence, the private RADV payload and
root-owned lifecycle state. It does **not** write `/boot`, select GRUB entries or
restart services. The authoritative stock amdgpu and stock initramfs are hashed and
never overwritten.

Source RPM downloads are cached under `/var/cache/bc250-llm-server/gfx1013/`. A
partial transfer remains as `.part`, is resumed on the next run, and is promoted to
the final cache object only after source-RPM identity/signature validation. Ctrl-C
is reported as operator interruption (exit 130), retains reusable source cache and
build evidence, and never commits partial lifecycle/boot state. Long `%prep`,
amdgpu and Mesa phases print elapsed-time heartbeats rather than fake percentages.

### Prepare failure reporting and evidence

A failed prepare emits one structured summary rather than several overlapping
messages. The primary `Stage:` is the exact active numbered stage with the numeric
prefix removed (for example `Fedora kernel %prep`), and `Cause:` is a classified
cause where one is known. If a failure is not recognized, the first meaningful
error line from the active stage log is surfaced as `unclassified — ...`; the CLI
does not report `unknown` when evidence contains a usable error.

The exact 1.16 device failure that motivated the 1.17 dependency repair was:

```text
kernel.spec:2216: Fixing Python shebangs...
+ %py3_shebang_fix tools/kvm/kvm_stat/kvm_stat ...
/var/tmp/rpm-tmp...: line 171: fg: no job control
error: Bad exit status ... (%prep)
```

This is classified as:

```text
Stage: Fedora kernel %prep
Cause: required RPM macro unavailable: py3_shebang_fix
```

The first 1.17 exact-device `prepare` after satisfying that macro dependency then
proved the expensive build stages but failed at the old mandatory `srcversion`
attestation. The module linked successfully and private RADV built successfully;
0.13.1-2.2 retains the release/device attestation parity introduced in 1.18 by using one shared validator and
treating absent `srcversion` as supplemental rather than fabricating it. Exact
vermagic and ABI checks remain mandatory.

Failure evidence remains root-only and bounded. Each failure/interruption keeps
the useful stage logs and `result.env` directory and also creates an actually
gzip-compressed `.tar.gz`; the archive is verified with both `gzip -t` and
`tar -tzf` before it is published. Module-attestation failures additionally retain
the built and stock module identities (`sha256sum`, `modinfo`, `readelf -n`) plus
the running kernel's `CONFIG_MODULE_SRCVERSION_ALL` setting when available. The
failure summary explicitly states that boot state and runtime/service state were not
changed and that reusable source cache was preserved.

`stage-boot` is a second transaction. It builds the dedicated patched initramfs from
an isolated copy/reflink of `/usr/lib/modules/<kernel>` via dracut `--kmoddir`,
requires the embedded `amdgpu` SHA-256 to match the prepared module, creates the
patched BLS, then selects it as one-shot `next_entry`. The saved/default entry remains
stock. A pre-existing one-shot selection is replaced only when it exactly matches the recorded verified-stock entry and saved/default authority is still that same stock entry. Any unknown/non-stock one-shot selection blocks before mutation and is left unchanged. An interrupted/failed `stage-boot` removes partial boot artifacts and restores
the previous `next_entry` while retaining the prepared build.

## Enabling private RADV

`enable` is accepted only while running the marked patched boot for the exact
prepared kernel and package identity. It revalidates:

- package patch/full-source manifests;
- exact prepared RPM identity;
- exact `kernel-devel` identity;
- prepared module hash/vermagic/ABI evidence;
- stock module/initramfs hashes;
- patched boot artifacts;
- private RADV and ICD hashes.

The private ICD is exercised headlessly after explicitly unsetting `DISPLAY`,
`WAYLAND_DISPLAY` and `XDG_SESSION_TYPE`. Promotion requires a RADV device with exact PCI vendor/device IDs `1002:13fe`,
a dedicated compute-only Vulkan queue family, and a prepared-module identity bound
to the exact staged BLS/initramfs SHA-256 values. If the prepared module carries a
`srcversion`, the loaded module must match it; when Fedora omits `srcversion`, the
project-owned exact-kernel/module/ABI/provenance plus staged-boot hash chain remains
a mandatory attestation path. The verified vendor/device/driver identity, Vulkan
summary hash and queue family are recorded in lifecycle state.

Private RADV is scoped only to `ollama.service` through
`/etc/systemd/system/ollama.service.d/70-bc250-gfx1013.conf`. No global
`/etc/environment` change and no user-wide Vulkan environment generator is
installed.

### Stock-kernel/stale-kernel guard

The Ollama drop-in has two independent runtime protections:

1. a systemd kernel-command-line condition requiring the package patched-boot
   marker; and
2. a privileged `ExecCondition` that rechecks package identity, exact prepared
   kernel, patched marker, staged BLS/initramfs hashes, private RADV/ICD hashes and,
   when the prepared module carried it, the amdgpu `srcversion`.

This matters after a Fedora kernel update. If a later stock kernel boots while
an old GFX1013 profile remains recorded, `ollama.service` fails closed while the private-RADV drop-in remains installed;
it will not start with that patched Mesa path against a stock/unrelated kernel.
`sudo bc250 gfx1013 status` reports `ROLLBACK_REQUIRED`, and the operator must
disable/reset and prepare again for the new exact kernel.

`enable` requires Ollama to be active. It writes the private-RADV drop-in and
restarts/smoke-tests Ollama while the saved/default boot is still stock. Only after
that live workload path succeeds is the patched entry promoted to saved/default.
Failure removes the drop-in and restores stock boot authority. A hard hang during
the smoke therefore cannot pre-promote the experimental boot as the default.

## Disable, recovery and package transactions

`disable --check` proves that a safe stock BLS target is available without
changing the machine. `disable` then performs rollback in this order:

1. resolve a safe stock BLS entry, preferring the current running stock kernel
   when appropriate;
2. set and verify that entry as saved/default;
3. set and verify it as the next boot;
4. remove the Ollama private-RADV drop-in;
5. remove package patched BLS/initramfs/private-RADV/prepared state;
6. re-verify stock boot authority.

A kernel update therefore does not force rollback to an obsolete prepared
kernel when a safe current-kernel stock BLS entry exists.

`reset` is the recovery path for missing/invalid lifecycle metadata with
package-owned remnants. It follows the same stock-first authority and cleans
only package-owned GFX1013 paths after the stock saved + next boot proof.

RPM upgrades also invoke the currently installed GFX1013 helper before payload
replacement. A prepared/enabled old RPM profile must be restored to stock boot
before a new RPM identity can replace it. Final RPM erase uses the same
fail-closed rollback rule. A failure to prove stock boot aborts the package
transaction rather than deleting recovery state.

If `disable` or `reset` is run while the patched kernel is currently loaded,
stock saved + next boot is still restored immediately, but a reboot is required
to unload the running patched module.

## Reboot-aware LLM A/B benchmark

Release 1.7 adds a bounded package-owned screen that **never changes boot or GFX
lifecycle state itself**. The operator performs the normal lifecycle transitions between
phases:

```bash
# A1: same candidate package, stock boot and GFX1013 DISABLED
sudo bc250 gfx1013 benchmark stock

# normal lifecycle transition
sudo bc250 gfx1013 prepare
sudo bc250 gfx1013 stage-boot
# reboot into the one-shot patched entry
sudo bc250 gfx1013 enable

# B: same package/kernel/model digests, GFX1013 ENABLED
sudo bc250 gfx1013 benchmark gfx

# restore the stock path
sudo bc250 gfx1013 disable
# reboot stock

# A2: restored-stock control
sudo bc250 gfx1013 benchmark restored
sudo bc250 gfx1013 benchmark report
```

Standard and Advanced are measured by default; `--include-deep` adds one bounded
Deep confirmation and is fixed by the A1 campaign. The campaign fixes the package
NEVRA, running kernel, exact Ollama model digests, prompt hash, warm-repeat count,
decode bound and telemetry interval. Later phases refuse identity drift. Evidence is
written below `/var/lib/bc250-llm-server/gfx1013/benchmarks/` with closed SHA-256
manifests. Failed phase attempts are sealed separately instead of overwriting valid
phase evidence.

Each phase captures cold load, TTFC/TTFA, prompt processing rate, generation rate,
run spread, allocated context, resident memory/VRAM, minimum `MemAvailable`, swap
growth, memory PSI, GPU clock/temperature, `ollama.service` restarts, GPU-fault journal
signatures, residency restoration and a fixed-seed deterministic output identity.
`report` compares A1 -> B and A1 -> A2 and refuses `PROMOTION_CANDIDATE` when the
GFX output identity differs from stock or repeated deterministic output is unstable.

`PROMOTION_CANDIDATE` is deliberately conservative and advisory. It requires all of:

- A2 restored-stock evidence;
- at least one >=5% prompt/decode throughput signal with no throughput regression worse
  than 3%;
- <=10% run CV for measured prompt/decode rates;
- <=5% restored-stock throughput drift;
- no GPU-fault signatures or Ollama restarts and complete GPU-journal evidence;
- successful residency restoration;
- GFX `MemAvailable` staying above the 128 MiB hard floor;
- no >128 MiB additional peak swap growth versus stock; and
- observed GFX GPU temperature below 85 C.

Even a clean `PROMOTION_CANDIDATE` does **not** enable GFX1013 by default. Product
quality review and operator acceptance remain separate authorities.

## Qualification boundary

The package reference kernel remains `7.2.9-200.fc44.x86_64`. Other Fedora
kernels are never allowed to reuse its module artifact; they require their own
exact-kernel preparation.

GFX1013 remains experimental/default-off after a successful build. Promotion
requires exact-device LLM A/B evidence comparing the same 0.13.1-2.2 package in
stock and GFX1013 modes, plus a clean stock restore control. Measure prompt
processing, generation, TTFT/load behavior, memory/swap/PSI, thermals, service
restarts and GPU/device-loss faults. Upstream gaming gains are useful motivation,
not proof of an Ollama inference gain.

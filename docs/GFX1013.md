# Experimental GFX1013 compute-queue profile

Release 0.13.1-1.10 keeps GFX1013 **opt-in, experimental and default-off**. It
retains the stock-first/Secure-Boot/rollback protections and incorporates the
exact-device 1.9 prepare/build repairs before any patched-boot performance claim.

The package profile is `v0.2.2-alpha`, based on
`DryhoppedIPA/bc250-gfx1013-fix` `0.2.0-alpha` commit
`d3e6dc062c34d2523db0abe5741d1f5b0dea00d9`.

This package profile deliberately enables only:

- the three pinned V33 kernel compute-queue lifecycle patches; and
- private Mesa/RADV `0001-gfx1013-compute-queue-fix.patch` against exact Fedora 44
  `mesa-26.2.4-1.fc44` / Source0 `mesa-26.2.4.tar.xz`
  (`sha256:bce5f7fbebb934373b86c999a064d52fb5065878dc57f287f95346648ec832e9`).

Mesa 26.2.1 already upstreamed the GFX1013 GFX10.1 IP-version correction, so
profile v0.2.2-alpha no longer carries that stale hunk. The private patch now
contains only the still-required compute-queue exposure and async-compute
threadgroup workaround.

The optional upstream mesh/task patches, 40-CU changes, FSR changes, fan/power
policy and unrelated toolkit changes remain outside this profile. The existing
live CU manager remains a separate stock-AMDGPU feature.

The package carries `PATCH-SHA256SUMS` and `SOURCE-SHA256SUMS` under
`/usr/share/bc250-llm-server/gfx1013/upstream/`. `prepare` verifies both before
building. Exact Fedora kernel-source identity, exact `kernel-devel` ownership,
built-module SHA-256/vermagic/symbol-version evidence, stock module/initramfs
hashes, Mesa source identity and private RADV/ICD hashes are persisted in
root-owned lifecycle state.

## Commands

Read-only state:

```bash
sudo bc250 gfx1013 status
sudo bc250 gfx1013 status --json
```

Non-destructive prerequisites/rollback checks:

```bash
sudo bc250 gfx1013 prepare --check
sudo bc250 gfx1013 disable --check
sudo bc250 gfx1013 reset --check
```

Lifecycle:

```bash
sudo bc250 gfx1013 prepare
# reboot once into the staged patched entry
sudo bc250 gfx1013 status
sudo bc250 gfx1013 enable
sudo bc250 gfx1013 disable
```

Recovery from orphaned/invalid package-owned GFX state:

```bash
sudo bc250 gfx1013 reset
```

`reset` is deliberately not a force-delete operation. It must first prove and
commit a safe stock saved/default **and next** boot path. If that authority
cannot be established, reset refuses destructive cleanup.

## Lifecycle states

`status` and `status --json` expose one top-level state:

| State | Meaning |
|---|---|
| `DISABLED` | No package-owned prepared/active GFX1013 profile exists. |
| `PREPARED` | Exact-kernel artifacts are prepared; stock remains authoritative. |
| `PATCHED_BOOT_UNVERIFIED` | The marked one-shot patched boot is running, but `enable` has not committed it. |
| `ENABLED` | The verified patched boot is saved/default and Ollama private RADV is enabled. |
| `STALE_KERNEL` | The running kernel differs from the prepared kernel; rollback/reprepare is required. |
| `ROLLBACK_REQUIRED` | State or boot authority is inconsistent and must be restored before promotion/reuse. |
| `BROKEN` | Risky package-owned artifacts exist without valid lifecycle state, or state validation failed. |

Only `DISABLED` and `ENABLED` are stable qualification states. `PREPARED`,
`PATCHED_BOOT_UNVERIFIED` and `STALE_KERNEL` are intentionally treated as
transitional/incomplete by the package gate. `ROLLBACK_REQUIRED` and `BROKEN`
are defects until repaired.

## Secure Boot policy

`prepare` determines Secure Boot state before any build/staging work. The
package-owned local `amdgpu` build is not automatically signed and the package
does not enroll a MOK key. Therefore:

- Secure Boot disabled: preparation may continue;
- non-EFI boot: preparation may continue;
- Secure Boot explicitly unsupported (`mokutil`: `This system doesn't support Secure Boot`): report `disabled-unsupported` and preparation may continue;
- Secure Boot enabled: preparation fails closed;
- Secure Boot state genuinely unknown on EFI: preparation fails closed.

An operator-managed signing/enrollment policy may be used outside this package,
but 0.13.1-1.10 deliberately does not automate trust enrollment or private-key
management.

## Exact-kernel preparation

`prepare --check` performs the non-destructive prerequisites check. It verifies,
among other things:

- Fedora/non-Atomic host policy;
- BC-250 PCI identity `1002:13fe`;
- package patch/full-source manifests;
- Secure Boot policy;
- required tools and named optional build RPMs, including the Fedora Mesa Cargo toolchain (`cargo`, `rust`, `cargo-rpm-macros`);
- exact `/lib/modules/$(uname -r)/build` ownership by
  `kernel-devel-$(uname -r)`;
- stock distro `amdgpu` module path;
- exactly one safe stock BLS entry for the running kernel;
- current saved/default boot is that stock entry;
- no conflicting upstream GFX1013 installation;
- no stale package patched-BLS/initramfs/private-RADV artifacts.

The mutating `prepare` then downloads/verifies the exact Fedora kernel SRPM and
runs that SRPM's own `%prep` in an isolated rpmbuild tree. The package derives
every AMDGPU file touched by the V33 patch set, requires exactly one Fedora-prepared
source tree containing all of those targets, fingerprints those prepared files, and
uses that prepared tree itself as patch/build authority. It does not substitute
pristine Source0 or an SRPM-text heuristic for Fedora's downstream source
transformations. The package then adapts the AMD trace include paths deliberately
for an external-module build, applies the pinned V33 patches with zero fuzz and
builds `amdgpu`. Module compatibility verification
follows the exact kernel configuration: with `CONFIG_MODVERSIONS=y` it compares
required symbol CRCs; without modversions it requires exact vermagic plus all
strong imported symbols to resolve in the exact build tree's `Module.symvers`.
The latter is an exact-kernel symbol compatibility check, not a claim of complete
ABI equivalence. `.ko`, `.ko.xz`, `.ko.zst` and `.ko.gz` artifacts are supported.

Private RADV is built from exact Fedora `mesa-26.2.4-1.fc44`. The Fedora release
gate reconstructs the SRPM `%prep` tree and requires the carried Mesa patch to
dry-run/apply with zero fuzz. Runtime `prepare` repeats the exact SRPM/Source0
identity and patch checks before staging `/opt/bc250-gfx1013/...`.

The private ICD is rewritten to reference the exact private
`libvulkan_radeon.so` path. It never relies on a system-wide Mesa replacement.

### Transaction boundary

Fedora kernel `%prep`, external module compilation, compatibility verification
and the Fedora-prepared Mesa build happen under a temporary root first. Package
lifecycle paths under `prepared/`, `/opt` and `/boot` are created only after those
build inputs have validated. Generating the dedicated patched initramfs uses an
isolated copy/reflink of `/usr/lib/modules/<kernel>` via dracut `--kmoddir`; only
the staged amdgpu is replaced. The authoritative stock amdgpu and stock initramfs
are hashed before/after and are never written by `prepare`.

Any pre-commit failure returns/remains `DISABLED`, restores and verifies the prior
GRUB `next_entry` before deleting patched boot artifacts, and then removes package
patched BLS/initramfs/private-RADV/prepared artifacts. If boot-manager restoration
fails, the lifecycle enters `SAFETY_FAILURE`/recovery-required state and preserves
the patched boot artifacts and recovery metadata rather than deleting the only
path needed to repair the transaction. Normal failures retain a root-only
diagnostic bundle under
`/var/lib/bc250-llm-server/gfx1013/failures/`. Only the newest five failed-prepare
bundles are retained. A failure bundle records the stage/reason, package/kernel/
source identities and available kernel/Mesa build logs; it is evidence only and
never counts as lifecycle state.

The dedicated patched initramfs is unpacked and required to contain exactly one
`amdgpu` module whose SHA-256 matches the newly built artifact before a BLS entry is accepted. `prepare` never changes the
saved/default stock boot; only the patched entry is selected as one-shot
`next_entry` after lifecycle state is committed.

## Enabling private RADV

`enable` is accepted only while running the marked patched boot for the exact
prepared kernel and package identity. It revalidates:

- package patch/full-source manifests;
- exact prepared RPM identity;
- exact `kernel-devel` identity;
- prepared module hash/vermagic/ABI evidence;
- stock module/initramfs hashes;
- patched boot artifacts;
- private RADV and ICD hashes.

The private ICD is then exercised with `vulkaninfo --summary`. Promotion
requires a RADV device with exact PCI vendor/device IDs `1002:13fe`. The
verified vendor ID, device ID, driver name and a SHA-256 of the Vulkan summary
are recorded in lifecycle state.

Private RADV is scoped only to `ollama.service` through
`/etc/systemd/system/ollama.service.d/70-bc250-gfx1013.conf`. No global
`/etc/environment` change and no user-wide Vulkan environment generator is
installed.

### Stock-kernel/stale-kernel guard

The Ollama drop-in has two independent runtime protections:

1. a systemd kernel-command-line condition requiring the package patched-boot
   marker; and
2. a privileged `ExecCondition` that rechecks package identity, exact prepared
   kernel, patched marker, private RADV/ICD hashes and, when exported by the
   loaded module, the amdgpu `srcversion`.

This matters after a Fedora kernel update. If a later stock kernel boots while
an old GFX1013 profile remains recorded, `ollama.service` fails closed while the private-RADV drop-in remains installed;
it will not start with that patched Mesa path against a stock/unrelated kernel.
`sudo bc250 gfx1013 status` reports `STALE_KERNEL`, and the operator must
disable/reset and prepare again for the new exact kernel.

If Ollama was active during `enable`, it must restart successfully on the
verified patched boot with the private ICD before activation commits. Failure
removes the drop-in and restores the previous saved/default boot.

## Disable, recovery and package transactions

`disable --check` proves that a safe stock BLS target is available without
changing the machine. `disable` then performs rollback in this order:

1. resolve a safe stock BLS entry, preferring the current running stock kernel
   when appropriate;
2. set and verify that entry as saved/default;
3. set and verify it as the next boot;
4. remove the Ollama private-RADV drop-in;
5. remove package patched BLS/initramfs/private-RADV/prepared state;
6. re-verify stock boot authority.

A kernel update therefore does not force rollback to an obsolete prepared
kernel when a safe current-kernel stock BLS entry exists.

`reset` is the recovery path for missing/invalid lifecycle metadata with
package-owned remnants. It follows the same stock-first authority and cleans
only package-owned GFX1013 paths after the stock saved + next boot proof.

RPM upgrades also invoke the currently installed GFX1013 helper before payload
replacement. A prepared/enabled old RPM profile must be restored to stock boot
before a new RPM identity can replace it. Final RPM erase uses the same
fail-closed rollback rule. A failure to prove stock boot aborts the package
transaction rather than deleting recovery state.

If `disable` or `reset` is run while the patched kernel is currently loaded,
stock saved + next boot is still restored immediately, but a reboot is required
to unload the running patched module.

## Reboot-aware LLM A/B benchmark

Release 1.7 adds a bounded package-owned screen that **never changes boot or GFX
lifecycle state itself**. The operator performs the normal lifecycle transitions between
phases:

```bash
# A1: same candidate package, stock boot and GFX1013 DISABLED
sudo bc250 gfx1013 benchmark stock

# normal lifecycle transition
sudo bc250 gfx1013 prepare
# reboot into the one-shot patched entry
sudo bc250 gfx1013 enable

# B: same package/kernel/model digests, GFX1013 ENABLED
sudo bc250 gfx1013 benchmark gfx

# restore the stock path
sudo bc250 gfx1013 disable
# reboot stock

# A2: restored-stock control
sudo bc250 gfx1013 benchmark restored
sudo bc250 gfx1013 benchmark report
```

Standard and Advanced are measured by default; `--include-deep` adds one bounded
Deep confirmation and is fixed by the A1 campaign. The campaign fixes the package
NEVRA, running kernel, exact Ollama model digests, prompt hash, warm-repeat count,
decode bound and telemetry interval. Later phases refuse identity drift. Evidence is
written below `/var/lib/bc250-llm-server/gfx1013/benchmarks/` with closed SHA-256
manifests. Failed phase attempts are sealed separately instead of overwriting valid
phase evidence.

Each phase captures cold load, TTFC/TTFA, prompt processing rate, generation rate,
run spread, allocated context, resident memory/VRAM, minimum `MemAvailable`, swap
growth, memory PSI, GPU clock/temperature, `ollama.service` restarts, GPU-fault journal
signatures and residency restoration. `report` compares A1 -> B and A1 -> A2.

`PROMOTION_CANDIDATE` is deliberately conservative and advisory. It requires all of:

- A2 restored-stock evidence;
- at least one >=5% prompt/decode throughput signal with no throughput regression worse
  than 3%;
- <=10% run CV for measured prompt/decode rates;
- <=5% restored-stock throughput drift;
- no GPU-fault signatures or Ollama restarts and complete GPU-journal evidence;
- successful residency restoration;
- GFX `MemAvailable` staying above the 128 MiB hard floor;
- no >128 MiB additional peak swap growth versus stock; and
- observed GFX GPU temperature below 85 C.

Even a clean `PROMOTION_CANDIDATE` does **not** enable GFX1013 by default. Product
quality review and operator acceptance remain separate authorities.

## Qualification boundary

The package reference kernel remains `7.2.9-200.fc44.x86_64`. Other Fedora
kernels are never allowed to reuse its module artifact; they require their own
exact-kernel preparation.

GFX1013 remains experimental/default-off after a successful build. Promotion
requires exact-device LLM A/B evidence comparing the same 0.13.1-1.10 package in
stock and GFX1013 modes, plus a clean stock restore control. Measure prompt
processing, generation, TTFT/load behavior, memory/swap/PSI, thermals, service
restarts and GPU/device-loss faults. Upstream gaming gains are useful motivation,
not proof of an Ollama inference gain.

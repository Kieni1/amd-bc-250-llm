## Finding 1 — Arena was still enabled

Authenticated inspection reported:

```text
evaluation.arena.enable = true
evaluation.arena.models = []
```

This exposed the generic `Arena Model` alongside the package's deliberately curated office roles.
For this single-user appliance, Arena is not a product role and an unrestricted Arena undermines the
role-oriented surface.

2.4 package decision: own `evaluation.arena.enable=false` through the existing authenticated Open
WebUI desired-state path. Do not create a custom Arena allowlist without a new product requirement.
Authenticated status must treat a later `true` value as drift.

and do not hide the dedicated embedding model unless it actually becomes a chat-selector model.
Authenticated desired-state status must detect missing/false hidden metadata while leaving unrelated
operator-owned model records untouched.

## Finding 3 — persisted local/offline and upload policy was not fully converged

The live DB already held the intended appliance values, including:

```text
FILE_MAX_SIZE = 128
FILE_MAX_COUNT = 20
ALLOWED_FILE_EXTENSIONS = package allowlist
openai.enable = false
direct.enable = false
code_execution.enable = false
code_interpreter.enable = false
memories.enable = false
ui.enable_community_sharing = false
ui.enable_signup = false
```

The operational issue was not current misconfiguration. The package's authenticated apply/status
contract did not own all of those persisted values, so a later admin/API change could survive package
convergence while status still reported no package-owned drift.

2.4 package decision: keep environment values as conservative fresh-database bootstrap defaults, but
also converge the persisted values above through the existing supported Open WebUI APIs. The package
owns `FILE_MAX_SIZE`, `FILE_MAX_COUNT`, the extension allowlist, Arena, external OpenAI/direct/code
execution/interpreter/memories/community-sharing. `ui.enable_signup=false` remains the existing
single-user bootstrap result and does not gain a second signup-management mechanism solely for this
finding. Extension-list drift comparison is order-insensitive.

## Deliberately rejected additions

Do not add from this investigation alone:

- another Open WebUI/backend/provider service;
- a custom Arena candidate pool;
- a separate model recommendation/default-order/pinning layer;
- a new generic configuration framework or direct database editing path;
- CORS changes without a demonstrated origin/exposure defect;
- changes to task/RAG/translation/MTP/Pi architecture;
- another RAG/model tournament.

The current package front door and firewall evidence make the upstream `CORS_ALLOW_ORIGIN='*'`
warning an optional hardening question, not a demonstrated exposure defect in this investigation.

## Bounded exact-device acceptance for 2.4

After a 2.4 RPM exists, one authenticated batch is sufficient:

1. confirm exact installed NEVRA and normal topology;
2. prove nginx and direct loopback Open WebUI HTTP health;
3. run `bc250-openwebui-setup status --verbose` and require clean desired state;
4. verify persisted Arena is disabled and Arena is absent from the ordinary product surface;
5. verify the six implementation models remain active but hidden;
6. verify the six curated office roles remain available;
7. verify title/tag tasks still use the dedicated task LFM;
8. smoke Standard / Documents / Higher Quality / Deep Reasoning and preserve translation/RAG health;
9. create one harmless persisted drift (prefer an upload-limit setting), prove status detects it,
   reconverge with apply, and prove clean state again;
10. finish with healthy `bc250-status`, authenticated `bc250-verify`, no leaked credentials and no
    temporary product-test state.

This does not justify another broad hardware or model qualification campaign.

### Pinned Open WebUI v0.11.3 API-adapter limitations

Controlled exact-device comparison found three upstream Ollama/OpenAI-style adapter issues:

```text
root max_tokens=64            not reliably enforced
nested options.num_predict=64 enforced
reasoning_content present     reasoning_tokens may still report 0
Ollama done_reason=length     OWUI finish_reason may report stop
```

These are real upstream v0.11.3 compatibility/observability limitations, not model, Ollama or BC-250
runtime failures. The package does not currently advertise Open WebUI `/api/chat/completions` as an
external compatibility contract. 2.4 therefore documents the limitations and preserves the
package-owned rule that hard Ollama generation caps use nested `options.num_predict`; it does not
vendor-patch the Open WebUI container solely for an unsupported external API surface. The existing
translation preset `params.max_tokens=2048` is a separate Open WebUI model-parameter path and was
reported working in the package product path.

If a future release intentionally promotes `/api/chat/completions` to a supported external interface,
qualify a newer Open WebUI release or a narrow reviewed adapter patch for all three semantics together.

### Exclusive-agent catalogue clarity

Open WebUI remained reachable in exclusive-agent mode while its persisted catalogue continued to list
normal office roles whose main/task backends were intentionally stopped. Requests failed promptly and
normal restoration was reliable. This is not a topology defect. 2.4 adds only operator guidance that
normal roles may remain listed but are unavailable until `sudo bc250-agent-mode normal`; it does not
dynamically mutate Open WebUI desired state during topology transitions.

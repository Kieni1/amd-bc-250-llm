# Installed 0.11.3-1.7 support / maintenance campaign — 2026-09-20

## Scope and evidence boundary

Installed package: `bc250-llm-server-0.11.3-1.7.fc44.x86_64` on the BC-250.
This campaign followed the completed exact-1.7 whole-appliance revalidation and
focused on support/maintenance behavior and operator UX. It is real-device evidence
for exact 1.7 only. Findings fixed in source release 1.8 are not device-qualified
until an exact 1.8 package is installed and retested.

The campaign intentionally stopped before backup restore, live upload deletion,
Pi forced-command shutdown and real idle S5/WOL after the safe-power busy/defer
case exposed a safety defect.

## Safe-power busy/defer failure

The deliberate busy/defer test ran over an established interactive SSH session:

```text
192.168.1.191:22 -> 192.168.1.118:39396
```

`sudo bc250-maintenance request-shutdown` should have deferred. Instead exact 1.7
entered the poweroff path far enough to broadcast shutdown and reset the SSH
connection before systemd canceled `bc250-night-shutdown.service`.

Root cause: `ss -Htn state established` presents endpoint columns as the final two
fields, but the guard tested fixed fields `$4`/`$5`, missing the local `:22` endpoint
on this host. Source 1.8 uses `$(NF-1)`/`$NF`, validates and handles the restricted
Pi control connection separately, and requests the final system power action with
`systemctl --no-block` after every guard passes.

The Pi path needs a narrow self-SSH exception once SSH detection is correct. Source
1.8 therefore preserves OpenSSH `SSH_CONNECTION` only for the dedicated forced-command
identity and exempts only that exact authenticated control tuple. Any second SSH or
other protected connection still defers. The public interactive `request-shutdown`
command has no bypass.

No real idle poweroff/S5/WOL or Pi forced-command shutdown is accepted from this 1.7
campaign. Those are exact-1.8 follow-up gates.

## Degraded-mode detection and recovery

Stopping `ollama-embedding.service` deliberately produced:

```text
mode=degraded
Mode: degraded (partial normal topology)
```

The verifier then failed the expected embedding/RAG reachability checks. Using the
supported normal-mode restoration path returned the appliance to normal topology;
final verification was clean and `systemctl --failed` reported zero failed units.
This is real-device confirmation of the 1.7 topology-classification correction.

## Model lifecycle blocks

The proposed experiment/agent unregister -> apply checks did not run. Their wrapper
used an unprivileged `[[ -f ... ]]` against manager-owned GGUF paths below the protected
`/var/lib/bc250-llm-server` tree, so the wrapper incorrectly interpreted inaccessible
files as absent and skipped. This was a test-wrapper defect, not evidence of package
model-lifecycle failure. Future device checks must use privileged existence/stat probes
and still avoid `refresh`/`remove` so verified GGUFs are retained.

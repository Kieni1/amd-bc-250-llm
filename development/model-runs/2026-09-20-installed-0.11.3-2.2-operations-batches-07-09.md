### Tika restart telemetry finding

A normal `systemctl restart tika.service` recovered successfully, but the old Tika/container process
exited with status 143 during the expected SIGTERM stop path. systemd temporarily recorded the old
instance as `Failed with result 'exit-code'` before the replacement instance started successfully.

This is misleading routine-administration telemetry, not a Tika runtime failure. Current 2.3 source
marks only exit status 143 as a successful expected Tika termination via `SuccessExitStatus=143`;
other abnormal exits remain failures. Real restart behavior must be retested on installed 2.3.

### Open WebUI readiness observation

After `open-webui.service` restart, systemd reached `active` before the application HTTP endpoint was
ready; useful HTTP readiness arrived roughly 20 seconds later. Current package paths that require
application readiness already use bounded HTTP/API probes, so no new health framework is required.
Service-active and application-ready remain distinct concepts.

## Batch 09 / 09C — reboot persistence and command-path defect

A real reboot using the working compatibility invocation:

```text
sudo reboot
```

reconstructed the appliance successfully. Post-reboot evidence included:

```text
boot ID changed
normal main/task/embedding topology returned
agent intentionally inactive
Open WebUI ready
nginx / office HTTP ready
maintenance timers active
firewalld active
live CU routing 40/40 healthy
persistent 40-CU activation intentionally disabled
failed units 0
bc250-verify 54 ok / 0 warn / 0 fail
```

Boot persistence is therefore healthy.

Repeated device evidence found a materially different result from:

```text
sudo systemctl reboot
```

The failing path did initiate shutdown and start a new kernel. The subsequent boot progressed through
systemd initialization, maintenance timers, live-CU reconstruction, USB Ethernet carrier/DHCP,
NetworkManager online state, nginx startup and normal Ollama listeners before the retained journal
ended abruptly. Boot history recorded that boot as a crash. The evidence does **not** establish Tika,
nginx, Ollama, 40-CU reconstruction, networking, the kernel restart transition, or generic systemd
shutdown as the root cause.

Audit/journal evidence distinguished the invocations as:

```text
COMMAND=/usr/sbin/systemctl reboot
COMMAND=/usr/sbin/reboot
```

Operational package rule from this evidence: package-controlled BC-250 reboot paths must avoid the
`systemctl reboot` invocation and use the proven compatibility invocation `/usr/sbin/reboot` (or
operator-facing `sudo reboot`). Do not deliberately rerun the known-bad path merely to reproduce the
problem again.

Current 2.3 source had exactly two executable package-owned `systemctl reboot` call sites, both in the
persistent 40-CU enable/disable helper. They now retain the existing automatic-reboot contract but
invoke `/usr/sbin/reboot`. No generic reboot wrapper was introduced.

## Decision / next gate

Preserve the already-proven restart resilience and firewall policy. On installed 2.3, retest only the
changed boundaries:

1. routine `tika.service` restart should recover without a false failed-result event from expected 143;
2. package-controlled 40-CU reboot paths must no longer execute `systemctl reboot`;
3. one real reboot using the supported package/operator workflow should reconstruct SSH, office HTTP,
   normal topology, maintenance timers, firewalld, live 40/40 and clean authenticated verification.

Do not reopen broad service, LAN-isolation or model qualification unless a changed boundary or new
failure justifies it.

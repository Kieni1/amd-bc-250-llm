# BC-250 Task-Model Handover — 2026-09-17

## Purpose

This is the current authoritative handover for the BC-250 background task-model workstream.

It summarizes the latest model/prompt/product-path experiments and records what should **not** be repeated in the next chat or workstream.

Newer source/package state and newer real-device evidence override this prose.

---

## Current decision

### Keep as production task model

`task-lfm25-1.2b-instruct-liquidai-q6-k`

Current conclusion:

- it remains the only tested model that combines useful task quality with proven safe background coexistence;
- it is not perfect, especially for tag robustness under concise first-turn context;
- no currently active challenger has demonstrated both higher quality and safe coexistence;
- do not replace it on the basis of the recent active-model campaign.

### Reject for the background task role

`exp-qwen3-4b-lmstudio-q6-k`

Reason:

- quality was promising: 5/6 in two independent cheap canonical screens;
- exact-source task staging caused global OOM;
- task-tuned staging at `num_ctx=4096` still caused global OOM during a tiny two-token survival request;
- the warm main GPT-OSS process was killed;
- Open WebUI/Tika/user processes were also OOM victims;
- therefore the model is not safe as a concurrent background task model on this BC-250 configuration.

This does **not** mean Qwen3 4B must be retired globally. The rejection applies to the concurrent task role with warm GPT-OSS.

## Stable production-task facts carried forward

### LFM SYSTEM result

The promoted LFM must **not** use the old generic fixed SYSTEM prompt.

Historical decisive result:

- LFM with generic SYSTEM: materially worse;
- no-SYSTEM LFM direct benchmark: 15/18;
- the fixed SYSTEM caused cross-contamination between task forms.

Current promoted Modelfile concept:

```text
no SYSTEM
num_gpu 99
num_keep 256
num_ctx 4096
num_predict 128
temperature 0.1
top_k 50
repeat_penalty 1.05
```

### Open WebUI prompt ownership matters

The model alone is not the product.

Historical result:

- LFM direct without generic SYSTEM: 15/18;
- real Open WebUI using upstream/default task prompts: 6/18;
- real Open WebUI using package-owned title/tag/query prompts: 15/18.

Therefore task quality is:

```text
model
+ model definition
+ package-owned prompt policy
+ Open WebUI routing/product path
```

Do not qualify a replacement from raw model output alone.

### Proven LFM coexistence

Earlier production LFM coexistence testing achieved:

- 9/9 true simultaneous GPT-OSS/LFM trials;
- task requests completed while the main model was actively generating;
- task model unloaded afterward;
- GPT-OSS remained resident;
- no serious OOM/GPU/device-loss/reset warnings;
- minimum observed MemAvailable in that campaign was about 962 MiB.

That remains the reference behavior for a production background task model.

## Tag-prompt work immediately before active-model screening

### Open WebUI tag lifecycle

Real Open WebUI 0.11.3 evidence showed:

- automatic chat tags are generated after the first completed assistant turn;
- the chat contains only two messages at that point;
- tags did not appear to refresh after the second turn in the tested lifecycle;
- API-persisted tags are the authoritative signal;
- visible UI chips are not a reliable quality gate.

This invalidated any prompt policy that assumes `<3 messages => General`.

### Candidate A

Outcome: rejected.

Strength:

- structurally clean.

Weakness:

- semantic collapse;
- frequently produced broad/generic tags instead of representing the distinct concrete concepts.

### Candidate B

Strong on the narrow canonical tag test, but superseded.

Reason:

- its `<3 messages => General` fallback conflicts with the observed real first-turn lifecycle.

### Candidate C

Important prompt:

```text
### Task:
Generate one flat list of 2-6 useful tags describing the chat.

Include both:
- broad topic tags, and
- specific concepts explicitly discussed in the chat.

When the chat contains multiple distinct concrete concepts, represent more than one of them rather than collapsing them into a generic process tag.
Use the chat's primary language.

When the chat has a clear topic, every tag must describe actual content from the chat. Do not use generic placeholder tags such as "General".
Use {"tags": ["General"]} only when there is genuinely no coherent topic.

Return exactly one raw JSON object with exactly one key:
{"tags": ["tag1", "tag2", "tag3"]}

Do not return a separate subtopic_tags or subtopics field.
Do not return multiple JSON objects.
Do not add markdown, explanations, or other text.

### Chat History (Open WebUI 0.11.3: latest 6 messages):
<chat_history>
{{MESSAGES:END:6}}
</chat_history>
```

Key French payload A/B:

- short/concise assistant context: 0/6;
- rich assistant context: 6/6;
- same user content;
- no meaningful swap growth;
- therefore the failure was context-shape sensitivity, not concurrency.

Typical weak concise output:

```json
{"tags":["Contrat","Clause","Livraison"]}
```

Typical rich-context output:

```json
{"tags":["Contrat","Résiliation","Paiement","Livraison","Pénalité"]}
```

### Candidate D

Outcome: rejected.

Exact short-context C/D:

- Candidate C: 0/6;
- Candidate D: 0/6.

Candidate D deterministically produced:

```json
{"tags":["Contrat","Obligations","Livraison"]}
```

The stronger instruction to preserve concrete user-message concepts merely replaced one broad abstraction with another and did not recover payment/termination/penalty detail.

### Current prompt conclusion

Do not immediately invent Candidate E.

The unresolved LFM issue is:

> robust tag extraction when the first assistant response is concise versus rich.

The next prompt work should be based on a broader first-turn corpus, not another single-case prompt micro-tuning loop.

## Active-model batch campaign — 2026-09-17

Two broad screens were run: compact, then extended.

The campaign itself completed cleanly:

- no infrastructure failure in the batch screen;
- exact restoration succeeded;
- credential scan succeeded;
- evidence archive creation succeeded.

### Important harness lesson

The first batch design had two advancement assumptions that were too strict:

1. it required the production baseline to be at least 5/6;
2. it required challengers to already be registered on the task lane.

Real evidence showed:

- production LFM canonical reference behaved around 4/6–5/6;
- most active challengers were registered only on the main lane.

Therefore future screening should separate:

```text
quality-screen eligibility
from
task-lane deployment eligibility
```

The production baseline should be used primarily as a drift/reference envelope, not as an absolute >=5/6 requirement.

### Compact/extended quality results of interest

#### Qwen3 4B LM Studio Q6-K

`exp-qwen3-4b-lmstudio-q6-k`

Result:

- 5/6 in the compact screen;
- 5/6 again in the extended screen;
- no systematic thinking/output-budget starvation;
- strongest active challenger by a clear margin.

This earned a focused task-lane staging experiment.

#### Gemma3 1B task control

`task-gemma3-1b-unsloth-ud-q4-k-xl`

Result:

- about 2/6;
- substantial language failures;
- remains a control/fallback, not a production challenger.

#### Other tested active candidates

The remaining compact/extended candidates were generally <=3/6.

Several showed explicit:

```text
output-budget
thinking-budget
empty-output
```

diagnostics.

No other model earned expensive task-role qualification.

## Qwen3 4B focused staging

### Attempt 1 — exact main-role definition copied to task lane

Source:

`exp-qwen3-4b-lmstudio-q6-k`

Source definition included:

```text
num_ctx 32768
num_gpu 99
num_keep 256
temperature 0.7
top_k 20
top_p 0.8
```

A temporary task-lane alias was created from the exact generated Ollama Modelfile.

Quality:

- 5/6 canonical;
- miss: French query generation;
- output quality was genuinely promising.

But coexistence failed catastrophically.

Observed kernel behavior:

- global OOM;
- warm main `llama-server` killed;
- Open WebUI/Tika/user processes also killed.

Conclusion:

- exact main-role definition is unsafe as a task configuration;
- quality score cannot override a coexistence failure.

Evidence:

`bc250-q3-stage-20260917-170719.tar.gz`

### Attempt 2 — task-tuned Qwen3 definition

To test whether the 32k context was the cause, a task-role alias preserved the same source model/template/SYSTEM/quantization but replaced runtime parameters with:

```text
num_gpu 99
num_keep 256
num_ctx 4096
num_predict 128
temperature 0.1
top_k 50
repeat_penalty 1.05
```

The task-tuned alias definition verification passed.

Then the campaign intentionally ran only a tiny survival request:

```text
Reply with exactly: OK
num_predict: 8
keep_alive: 0
```

The request itself succeeded:

```text
HTTP 200
response: OK
wall time: ~11.69 s
```

But resource/safety results were unacceptable:

```text
min MemAvailable:      100.28 MiB
start swap used:       528.10 MiB
peak swap used:       1243.20 MiB
swap growth:           715.10 MiB
resource gate:         false
```

Kernel evidence showed repeated global OOM activity.

Victims included:

- user `systemd`;
- Open WebUI Python process;
- Tika Java process;
- warm main `llama-server`.

The script correctly stopped before:

- concise DE/EN/FR quality probes;
- canonical campaign;
- full robustness;
- live Open WebUI qualification.

Evidence:

`bc250-q3-task-20260917-171403.tar.gz`

### Qwen3 task-role conclusion

```text
quality potential:      good (5/6 repeated)
task-role coexistence:  unsafe
final task-role result: REJECT
```

Do not spend more time on:

- 2k context experiments;
- smaller num_predict;
- minor sampling changes;
- prompt micro-tuning for task deployment.

The resident footprint itself is already incompatible with the required warm-main background-task role.

## What the next task-model stream should do

### Do

1. Keep production LFM 1.2B as the task-model reference.
2. Work on first-turn tag robustness using a diverse corpus.
3. Keep direct model quality separate from real Open WebUI product-path quality.
4. For a genuinely new compact candidate:
   - cheap quality screen;
   - **tiny warm-main survival gate**;
   - concise first-turn usefulness;
   - only then canonical repetition/product path/overlap.
5. Prefer genuinely compact candidates near the 1–2B footprint for the concurrent task role.

### Do not

- do not retest Qwen3 4B for the concurrent task role;
- do not run large models through full task qualification before survival testing;
- do not treat a good canonical score as a deployment result;
- do not weaken the evaluator to accommodate a candidate;
- do not require an already-registered task-lane model for the cheap quality screen;
- do not let a hard-coded baseline threshold invalidate useful challenger data;
- do not use visible UI tag chips as the primary persistence signal;
- do not archive raw auth/session material;
- do not generate SHA/checksum files as part of experiment scripts.
